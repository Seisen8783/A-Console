# 交接文档：手机端让微信小程序读到"干净"的轨迹坐标

> 记录时间：2026-11-20 18:40
> 目标平台：vivo Y33s（V2166A / Android 12 / SDK 31），备选 Mac 模拟器（API 37）
> 仓库：https://github.com/Seisen8783/NoReal

---

## 一、目标与验收标准

**目标**：微信（包括微信小程序）里读到的位置，是一条按配速展开的连续轨迹，且**不带系统打上的模拟定位标记**。

**验收标准**（必须同时满足）：

1. 应用读到的 `Location` 对象 `isMock == false`（Android 12+）/ `isFromMockProvider == false`（旧版本）
2. 坐标随轨迹连续推进，速度与方位角与设定配速一致
3. 不依赖 root，不破坏用户主号微信的本地数据
4. 全程在手机本地完成

---

## 二、为什么不能沿用"写系统定位源"

这是整条路线的第一个坑，也是所有后续设计的出发点。

NoReal 原有的做法是注册测试定位源（`addTestProvider` + `setTestProviderLocation`），这是系统提供的正规调试通道，代价是：

- Android 框架给这条 provider 产出的**每一个**坐标强制打上 `isMock = true`
  （源码位置：`LocationProviderManager`，dumpsys 里那个 `[mock]` 就是它）
- 腾讯位置服务（微信、小程序都走它）检查这个标记，命中就静默丢弃
- **实测表现**：系统层坐标在推进、微信位置共享绿点 25 秒不动，且不报任何错

已核实的框架事实（拉 AOSP android13/14/15 三个分支源码 grep 确认）：

- `cmd location` 只有测试定位源一条注入通道，`LocationShellCommand.java` 里**没有**任何关闭标记的参数
- AOSP 里唯一"官方且不带标记"的通道是 ADAS GNSS 注入，但被 `FEATURE_AUTOMOTIVE` 门禁锁着，
  非车机设备 `cmd location help` 根本不列这些命令
- 结论：**纯写入端这条路已经封死**，要骗过微信只能换注入路径

## 三、三条通道的现状

| 通道 | 机制 | 坐标带 mock 标记？ | 状态 | 备注 |
| --- | --- | --- | --- | --- |
| A. 系统测试定位源 | `addTestProvider` + `setTestProviderLocation` | **带** | 已实现 | 微信读不到；其他应用可读 |
| B. 接管模式 + LocBridge | 本机回环 UDP 广播坐标，模块在目标进程里自造 `Location` | **不带** | 链路已通，hook 未生效 | **主线** |
| C. 模拟器 GPS 硬件 | `adb emu geo fix` | **不带** | 坐标注入生效，但通道本身不稳 | 只作对照实验 |

### 通道 B 的完整链路

```
NoReal（手机本地）
  轨迹 + 配速 + 圈数 → 每秒一帧坐标
  接管模式：UDP 广播到 127.0.0.1:38765（只走回环，不出设备）
        │
        ▼
LocBridge（Xposed 模块，免 root 注入）
  订阅 127.0.0.1:38765 拿坐标
  hook android.location.LocationManager 的三条读取路径：
    getLastKnownLocation / getCurrentLocation / requestLocationUpdates
  交给应用的是 new Location(...) 构造的对象 → isMock 天然是 false
  另有 hook Location.isMock() → false 作为兜底
```

关键认知：**不是"把标记去掉"，而是"给一个本来就没有标记的坐标"**。
所以下游做多少交叉验证（WiFi/基站/卫星/轨迹合理性）都拦不住。

## 四、已完成并验证的部分

### 4.1 真机（vivo Y33s）接管模式广播链路 ✅

`LocProbe` 探针界面实测输出：

```
【系统定位】
[lastKnown] provider=gps lat=37.388522 lon=117.981327 acc=550.0 spd=0.25 brg=0.2 isMock=false
【本机坐标流】
lat=37.387647 lon=117.985121 spd=3.33 brg=46.3 lap=1 ts=1795169647819
```

- 本机坐标流 = NoReal 接管模式广播的轨迹坐标，速度 3.33 m/s 正好对应 5:00 配速 ✅
- 系统定位 = 真实位置（accuracy 550 m 的典型粗定位），**接管模式没有污染系统定位** ✅

### 4.2 模拟器对照实验 ✅（证明"无标记坐标在应用里读得到"）

模拟器注入北京天安门坐标后，探针读到：

```
provider=gps lat=39.9087 lon=116.3974 isMock=false
```

再把 NoReal 轨迹经 `adb emu geo fix` 推入模拟器 GPS 硬件通道，探针读到的系统定位
**就是 NoReal 的轨迹坐标**，且 `isMock=false`：

```
[17:35:42] geo fix 117.984335 37.388420
探针: system update provider=gps lat=37.38842 lon=117.984335 isMock=false
```

这就是微信将读到的值。

### 4.3 免 root 注入框架在真机上的可用性 ✅

- **NPatch 1.1.0 在这台 vivo 上 SIGILL 崩溃**（`Fatal signal 4 in NPatch-LogFlush`），
  它的 native 库在这台机器上执行非法指令，**不能用**
- **LSPatch v0.6 正常** ✅（API 93 / 框架 1.9.2）
- LSPatch CLI 用法：

  ```bash
  JAVA="/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/java"   # 需要 JDK 21+
  "$JAVA" -jar jar-v0.6-398-release.jar <target.apk> <module.apk> [...]        # 输出 target-398-lspatched.apk
  ```

- **模块自身也要 patch 一份**（`locbridge.apk` 同样要 patch），否则模块不会被加载
- NPatch/LSPatch 的 manager 都能识别我们的模块，模块描述与作用域正常显示

## 五、卡在哪：hook 系统框架类需要 Shizuku

LSPatch 有两种模式：

| 模式 | 能 hook 应用代码 | 能 hook 系统框架类 | 前置条件 |
| --- | --- | --- | --- |
| 嵌入模式（当前） | ✅ | ❌ | 无 |
| Shizuku 模式 | ✅ | ✅ | Shizuku 服务在跑 |

我们要 hook 的是 `android.location.LocationManager`——**系统框架类**，嵌入模式改不了它。
LSPatch 管理器首页当前显示「Shizuku 服务未连接，部分功能不可用」。

**Shizuku 的 APK 已下载**：`/tmp/sandbox/shizuku-v13.6.0.r1086.2650830c-release.apk`
（注意 `/tmp` 会被清理，长期保存请拷到项目或 `~/Downloads`）

用 adb 拉起 Shizuku（标准做法，无需 root）：

```bash
adb install -r /tmp/sandbox/shizuku-v13.6.0.r1086.2650830c-release.apk
# 首次需要先在手机上打开一次 Shizuku app
adb shell sh /storage/emulated/0/Android/data/com.rikka.shizuku.privileged.api/start.sh
adb shell ps -A | grep shizuku     # 确认服务进程存在
```

## 七、需要用户决策的点：微信怎么装

**LSPatch/NPatch 都不支持覆盖安装**（patch 后签名变了），所以 patch 微信必须**卸载原版再装**，
主号微信的本地聊天记录会丢（无 root 无法备份 `/data/data/com.tencent.mm`）。

| 方案 | 做法 | 主号风险 | 代价 |
| --- | --- | --- | --- |
| **甲：小号 patch 重装** | patch 微信 APK → 卸载原版 → 装 patched → 小号登录 | 无（主号换成小号） | 要重新登录；可能有模拟器/签名风控 |
| **乙：容器承载微信** | 手机上装容器（VirtualApp / 黑盒 / 应用市场"多开"），把微信装进容器，只 patch 容器 APK | 无 | 要下载容器；容器内微信也要重新登录；容器内能否注入需验证 |
| **丙：硬件 GNSS 欺骗** | 蓝牙 GNSS 欺骗器（¥100–300），手机当外设接收伪造 NMEA | 无 | 硬件成本；轨迹可控性一般 |

**推荐甲或乙**。无论哪种，链路都是通的：
宿主 NoReal 通过 `127.0.0.1:38765` 把坐标喂给容器/进程内的 LocBridge ✅（回环地址同机共享）。

## 八、踩坑清单（都踩过了，别再踩）

1. **UDP 的 ICMP 陷阱**（最隐蔽）
   `connect()` 过的 UDP socket，在对端没监听时会收到 ICMP port-unreachable，
   之后收发全部失败、线程静默死亡。模块总是比 NoReal 先启动，原来这条路径必然失效。
   → 订阅端一律**不 connect**，把目标地址写进 `DatagramPacket(buf, len, target)`，并定时重发 `SUB` 保活。
2. **Android 的 `DatagramSocket` 没有 `send(packet, addr)` 重载** → 目标地址写进 DatagramPacket 本身。
3. **包可见性**（Android 11+）
   targetSdk 30+ 的 app 若不声明 `<queries>`，找不到 NPatch 的配置 provider（模块注入读不到配置）
   和 LocBridge 的 provider（注册目标失败），日志是 "Failed to find provider info for ..."。
   → 探针 manifest 已加 `queries`：top.nkbe.npatch / com.noreal.locbridge / com.noreal.android。
   ⚠️ **微信自己的 manifest 不会有这些声明**，patch 微信时这是已知风险点。
4. **Android 8+ 起隐式广播不再送达 manifest receiver** → 必须用显式组件：
   `adb shell am broadcast -n com.noreal.android/.DebugReceiver -a <action>`
5. **manifest 上的 `android:permission="android.permission.DUMP"` 会让 adb shell 发不出去**
   → 已改成运行时校验 `Binder.getCallingUid()`（只接受 shell/root）。
6. **Android 12 后台启动前台服务受限** → 先 `am start` 把 NoReal 拉到前台，再发广播。
7. **logcat buffer 会被设备上的 GMS 日志冲掉** → 自动化脚本必须**流式抓**（`logcat > file &`），
   事后 `logcat -d` 会漏事件。
8. **模拟器 geo fix 通道不可靠**：API 37 镜像下 `adb emu geo fix` 返回 OK 但坐标不变
   （"Brokered program policy check unavailable"），`-gpu host` 与 swiftshader 都一样。
9. **模拟器进程会被工具会话回收** → 用 `python3 -c "import os; os.setsid(); os.execv(...)"` 启动才活得久。
10. **vivo 的 `adb shell input tap` 这次可用**；uiautomator dump 看不到 Compose 的 Switch 控件，要靠截图定位。
