# 微信定位链路技术分析：卡在哪，为什么卡

> 记录时间：2026-11-20 19:00
> 对应提交：`fdce57b`
> 对象：vivo Y33s（V2166A / Android 12 / SDK 31），微信 + 微信小程序

---

## 摘要

"微信过不去"不是一个 bug，是**两个不同层面的阻塞叠在一起**：

| 层 | 阻塞 | 性质 | 能否解 |
| --- | --- | --- | --- |
| 工程层 | LocBridge 模块根本没被加载进微信进程 | 工具链配置缺两环（Shizuku 未连接、模块未在管理器启用） | **能**，按步骤配齐即可 |
| 架构层 | 即使 hook 装上了，微信有两条绕开 Java 层的路径 | 技术设计问题 | 部分能，需扩大 hook 面 |

工程层的判断依据很硬：探针进程的日志里**一条 `[LocBridge] ...` 都没有**，
说明 `LocBridge.handleLoadPackage()` 从未被调用——模块连加载这一步都没走到，
谈不上 hook 失败。所以现在讨论"微信为什么还读不到"为时过早。

---

## 一、微信定位的完整链路（五层）

先把链路摊平，才知道每一刀能切在哪。

```
┌─ 第 1 层：小程序 JS ────────────────────────────────────────┐
│  wx.getLocation({type:'gcj02'})                              │
│  运行在微信的小程序逻辑层进程（:appbrand0 之类）              │
└───────────────────────┬──────────────────────────────────────┘
                        │ JSAPI 调用 → 微信内部 JSBridge
┌─ 第 2 层：微信 Java 层 ─────────────────────────────────────┐
│  微信自己的 LocationService / 权限校验 / 缓存                │
│  可能拆在多个进程：主进程、:appbrand、:tools                  │
└───────────────────────┬──────────────────────────────────────┘
                        │ ① Java 调用   或   ② native 直连
┌─ 第 3 层：定位入口 ─────────────────────────────────────────┐
│  ① android.location.LocationManager（Java API）              │
│  ② libwechatapp.so / 腾讯位置服务 .so 直接 binder transact    │
│     拿到 ILocationManager 代理，绕过 Java 层                  │
└───────────────────────┬──────────────────────────────────────┘
                        │ Binder IPC（ILocationManager）
┌─ 第 4 层：system_server ────────────────────────────────────┐
│  LocationManagerService                                      │
│  → LocationProviderManager（真实的 gps/network/fused）        │
│  → 给每个 ProviderRequest 打上 mock 标记（如果是测试 provider）│
└───────────────────────┬──────────────────────────────────────┘
                        │ Location 对象（含 isMock 字段）
┌─ 第 5 层：腾讯位置服务 SDK ─────────────────────────────────┐
│  拿到坐标后做多源交叉验证：                                   │
│  · GnssStatus：卫星数、信噪比、仰角方位角                     │
│  · WifiManager.getScanResults()：周边 BSSID                  │
│  · TelephonyManager：LAC/CID 基站                            │
│  · 轨迹合理性：速度、加速度、瞬移                             │
│  · 服务端：出口 IP 归属地、账号历史位置分布                    │
│  · Location.isMock() 标记                                    │
└─────────────────────────────────────────────────────────────┘
```

**关键点**：`Location.isMock()` 只是第 5 层众多判据里的**一条**。
我们原来的方案（LocBridge 在目标进程里替换 `Location` 对象）只能打掉这一条，
而第 5 层其余判据在**真机上天然为真**——WiFi 是家里的、基站是楼下的、卫星是头顶的。

## 二、为什么"写系统定位源"必然失败（已证）

NoReal 原有做法走第 4 层：

```java
manager.addTestProvider("gps", ...);        // 注册测试 provider
manager.setTestProviderLocation("gps", loc); // 写入坐标
```

AOSP 在这条路径上强制打标记，源码级证据：

```java
// frameworks/base/services/core/java/com/android/server/location/provider/LocationProviderManager.java
@Override
public void onReportLocation(LocationResult locationResult) {
    ...
    if (mProvider.isMock()) {          // dumpsys 里那个 [mock] 就是它
        ...
    }
}

// MockLocationProvider.setProviderLocation
Location location = new Location(l);
location.setIsFromMockProvider(true);   // 标记在这里被打死
mLocation = location;
reportLocation(LocationResult.wrap(location).validate());
```

所以：

- 应用拿到的 `Location` 对象 `isMock == true`
- 腾讯 SDK 第 5 层第一条判据命中 → 静默丢弃（**不报错、不提示**）
- 实测表现：`dumpsys location` 里 `gps provider [mock]`、`et=` 时间戳持续推进，
  但微信位置共享绿点 25 秒不动

并且这条路**没有任何参数能关掉标记**（已核实）：

- `LocationShellCommand.java`（android13/14/15 三分支）里只有 `add-test-provider` /
  `set-test-provider-location`，**没有 `--is-mock` 之类的开关**
- AOSP 唯一不带标记的官方通道是 ADAS GNSS 注入（`set-adas-gnss-location`），
  但整段代码包在 `if (mContext.getPackageManager().hasSystemFeature(FEATURE_AUTOMOTIVE))` 里，
  非车机设备 `cmd location help` 连命令都不显示

## 三、卡点 A（工程层）：模块没被加载

### 3.1 现场证据

探针进程（已 patch 并传入 LocBridge 模块）启动时的日志：

```
E locbridge.prob: Not starting debugger since process cannot load the jdwp agent.
E ActivityThread: Failed to find provider info for top.nkbe.npatch.manager.provider.config
E locbridge.prob: expected 3 dex files but found 1
E ActivityThread: Failed to find provider info for com.noreal.locbridge.provider
```

**没有任何 `[LocBridge] ...` 日志**。

而 `LocBridge.handleLoadPackage()` 的第一件事就是打日志：

```kotlin
XposedBridge.log("[LocBridge] hooked ${lpparam.packageName} in ${lpparam.processName}")
```

一条都没有 → `handleLoadPackage` 没被调用 → **模块没被加载**，不是 hook 失败。

### 3.2 模块没加载的三个原因

**原因 1：模块没有在管理器里启用作用域**

LSPatch/NPatch 的 CLI 把模块 APK 塞进打补丁后的包，只是"**随包携带**"，
还需要在管理器里给目标应用**显式启用**这个模块（决定作用域）。这一步没做，模块就不会被加载。

**原因 2：LSPatch 嵌入模式对系统框架类的限制**

这是更根本的一层。要 hook 的 `android.location.LocationManager` 属于 **boot classpath 类**，
由 `BootClassLoader` 加载，不是应用自己的类。

LSPatch 有两种运行模式：

| 模式 | 原理 | 能 hook 应用自身代码 | 能 hook 系统框架类 | 前置条件 |
| --- | --- | --- | --- | --- |
| 嵌入模式（当前） | 把 loader dex + native 库塞进目标 APK，应用启动时在同一进程内加载 hook 引擎（LSPlant，inline hook ArtMethod） | ✅ | ⚠️ 受限 | 无 |
| Shizuku 模式 | 借用 shell 权限（uid 2000）启动特权进程，向目标进程注入 | ✅ | ✅ | Shizuku 服务在跑 |

LSPatch 管理器首页当前明确写着：

```
Shizuku 服务未连接，部分功能不可用
```

"部分功能"里就包括对**系统框架作用域**的支持。我们要 hook 的正是系统框架类，所以必须补上 Shizuku。

**原因 3：Android 11+ 的包可见性（已修，但暴露了设计风险）**

`Failed to find provider info for com.noreal.locbridge.provider` 是包可见性导致的：
targetSdk 30+ 的应用若不在 manifest 里声明 `<queries>`，就看不到别的包的 provider。

这带来两个后果：
- 探针无法把自己注册成 LocBridge 的目标（我们已在探针 manifest 加 `queries` 修掉）
- ⚠️ **微信的 manifest 里不可能有这些声明**，patch 微信时这条风险依然存在
  （LocBridge 读配置、探针注册目标都依赖跨包 provider）

### 3.3 补这一环的完整步骤

```bash
# ① 装 Shizuku 并拉起（shell 权限，不需要 root）
adb install -r ~/Downloads/noreal-handoff/shizuku-v13.6.0.r1086.2650830c-release.apk
# 手机上先打开一次 Shizuku 完成初始化
adb shell sh /storage/emulated/0/Android/data/com.rikka.shizuku.privileged.api/start.sh
adb shell ps -A | grep shizuku

# ② LSPatch（org.lsposed.lspatch）设置里切到 Shizuku 模式
# ③ 应用 → LocProbe → 模块 → 勾选 LocBridge → 启用 → 强制重启
# ④ 判定
adb logcat -c && adb shell am force-stop com.noreal.locbridge.probe
adb shell am start -n com.noreal.locbridge.probe/.LocProbeActivity
sleep 6
adb logcat -d | grep -E "LocBridge|hooks installed"
```

**判定标准**：

1. `[LocBridge] LocationManager hooks installed` 出现 → 模块加载成功、hook 装上了
2. 探针界面「系统定位」变成 NoReal 的轨迹坐标且 `isMock=false` → **端到端通了**

如果第 1 条出现但第 2 条不成立 → 进入卡点 B。

## 四、卡点 B（架构层）：即使 hook 装上，还有两道关

### 4.1 第一道：微信可能根本不走 Java 层

`LocationManager` 只是 Java API。任何 native 代码都可以直接拿到 `ILocationManager` 的 binder 代理：

```cpp
// 伪代码：native 直连，完全绕过 Java 层
sp<IServiceManager> sm = defaultServiceManager();
sp<IBinder> binder = sm->getService(String16("location"));
sp<ILocationManager> lm = interface_cast<ILocationManager>(binder);
lm->requestLocationUpdates(request, listener, packageName, attributionTag);  // 直接 IPC
```

腾讯这类厂商的 SDK（`libwechatapp.so`、腾讯位置服务的 `.so`）在 native 层直连系统服务是常规做法——
为了绕过 Java 层的权限包装、降低延迟、也顺便躲开 Java 层 hook。

**如果微信走这条路，我们在 Java 层替换 `Location` 对象就是空转**：
`LocationManager.requestLocationUpdates` 一次都不会被调用，`FixSource.hits` 计数会一直是 0。

**这是可验证的，判断方法**：

```bash
# 看 LocBridge 的命中计数（LocBridge 界面里的"命中 N 次"）
# 或者看 dumpsys 里微信的定位注册
adb shell dumpsys location | grep -A3 "registration com.tencent.mm"
```

- `hits > 0` 且微信仍读真实位置 → 走的是 Java 层，但被第 5 层判据拦了
- `hits == 0` 且微信能定位 → **走的是 native 直连**，Java hook 无效，必须改 hook 点

改法（如果确认是 native 直连）：

| 方案 | 做法 | 需要 |
| --- | --- | --- |
| hook system_server | 在 `system_server` 里 hook `LocationManagerService` / `LocationProviderManager.onReportLocation`，按 uid 过滤只替换微信的请求 | root 或 Shizuku + 系统框架作用域 |
| hook native 函数 | inline hook `IServiceManager::getService` / `IPCThreadState::transact` | 需要 Frida（root）或自写 PLT hook |
| 换容器 | 让微信跑在容器里，容器整体提供定位 | 见第五、六节 |

**注意**：hook `system_server` 影响面大（所有应用共享同一个 `LocationManagerService`），
必须按 `ProviderRequest` 的 uid 精确过滤，否则会把整机定位改掉。

### 4.2 第二道：第 5 层的多源交叉验证（真机上无解的部分）

这是"再真一点"也没用的原因。腾讯位置服务在真机上拿到的判据全是真值：

| 判据 | 真机上的值 | 我们的伪造能力 |
| --- | --- | --- |
| `Location.isMock` | 可被 hook 改 false | ✅ 能（这是唯一能改的） |
| GnssStatus 卫星数 / 信噪比 | 头顶真实卫星 | ❌ 未伪造（要 hook `GnssStatus`，构造隐藏类） |
| WiFi BSSID 列表 | 家里/学校真实 AP | ❌ 未伪造（要 hook `WifiManager.getScanResults`） |
| 基站 LAC/CID | 真实基站 | ❌ 未伪造（要 hook `TelephonyManager`） |
| 轨迹合理性 | 我们按配速展开，**这一项是达标的** | ✅ 速度 3.33 m/s、方位角连续变化 |
| 出口 IP 归属地 | 真实运营商 IP | ❌ 未处理（要 VPN/代理，且与坐标城市一致） |
| 服务端账号画像 | 账号历史位置分布 | ❌ 服务端判定，客户端无解 |

**数学上讲**：设每条判据的伪造难度为 1，真机要同时让 5–6 条互相作证，
且其中至少两条（IP、服务端画像）**不在客户端可控范围**。

这就是为什么"坐标改得再真"也没用——**问题不在坐标，在环境**。

### 4.3 为什么模拟器/云手机能过

反过来看就清楚了：模拟器里**整套环境都是假的**，所以交叉验证自洽。

| 判据 | 模拟器里的值 | 结果 |
| --- | --- | --- |
| 坐标 | `adb emu geo fix` 注入虚拟 GPS 硬件 | 无 mock 标记（**已实测 `isMock=false`**） |
| 卫星 | 模拟器 GNSS HAL 生成（satellites=0 或模拟值） | 与"室内"场景自洽 |
| WiFi | 模拟器虚拟 WiFi（AndroidWifi 等固定 AP） | 与坐标不矛盾（都是"模拟环境"） |
| 基站 | 模拟器虚拟基站 | 同上 |
| IP | 宿主机 IP | ⚠️ 唯一可能露馅的点 |
| 设备指纹 | 模拟器指纹 | ⚠️ 微信有模拟器检测 |

实测已确认：模拟器里探针读到 `provider=gps lat=39.9087 lon=116.3974 isMock=false`，
把 NoReal 轨迹经 `geo fix` 推入后，系统定位**就是轨迹坐标且无标记**：

```
[17:35:42] geo fix 117.984335 37.388420
探针: system update provider=gps lat=37.38842 lon=117.984335 isMock=false
```

**"无标记坐标应用确实会收"这一点已经被证实**，剩下的是"环境自洽"和"微信的模拟器检测"。

## 五、真机上要"全通"需要的完整改造清单

按性价比排序。前提都是**不动主号微信数据**。

### 方案甲：容器承载微信（推荐）

```
手机
├─ NoReal（宿主）── 回环 UDP 127.0.0.1:38765 ──┐
└─ 容器（VirtualApp/黑盒/多开类）                 │
    └─ 微信（容器内）← LocBridge 模块 ←──────────┘
        容器提供：虚拟定位 + 虚拟 WiFi + 虚拟基站 + 虚拟设备指纹
```

- 容器本身就是"环境整体为假"的缩微版：主流多开容器都会伪造 IMEI、AndroidID、WiFi 信息
- 微信装在容器里，**主号零风险**（数据完全隔离）
- 容器内重装微信不涉及主号卸载
- 链路与当前完全一致：宿主 NoReal 广播 → 容器内 LocBridge 订阅（回环地址同机共享）
- 待验证：容器内能否注入（用 LSPatch patch 容器 APK，或在容器内二次 patch 微信）

### 方案乙：小号 patch 重装微信

- `LSPatch jar → 微信 APK → patched APK → 卸载原版 → 安装 → 小号登录`
- 主号不受影响（因为主号在另一台设备/或换成小号）
- 风险：微信有签名自校验与模拟器/改包检测，可能闪退或触发风控
- **需要在 Shizuku 模式下 patch 才有系统框架作用域**

### 方案丙：硬件 GNSS 欺骗器

- 蓝牙/USB 形态的 NMEA 发生器（¥100–300），手机把它当外部 GNSS 接收机
- 第 3、4 层完全绕过（驱动层收到的就是"真"卫星数据）→ **无 mock 标记**
- 第 5 层的卫星判据也自然满足（NMEA 里带卫星数、信噪比、仰角）
- 局限：多数模块只支持定点，连续轨迹要 SDR（HackRF + gps-sdr-sim，¥1500+）
- **这是真机上唯一能同时满足"无标记 + 卫星数据自洽"的软硬件组合**

### 方案丁：root + 全套 hook

- 需要 root（这台 vivo 无 root，且 2017 年机型官方解锁渠道已关）
- 要 hook 的面：`LocationManager`、`Location.isMock`、`GnssStatus`、`WifiManager.getScanResults`、
  `TelephonyManager.getAllCellInfo`、`SystemProperties`（机型指纹）
- 再加上 IP 处理（VPN 出口与坐标城市一致）
- 工程量大，且服务端画像仍可能判定；**不推荐在这台机器上做**

## 六、当前状态与"下一步"的精确判据

### 已完成（有实证）

| 项 | 证据 |
| --- | --- |
| 写系统定位源会被打标记 | AOSP 源码 + 实测 dumpsys `[mock]` |
| `cmd location` 无关闭标记的参数 | android13/14/15 三分支 grep |
| 无标记坐标应用会收 | 模拟器探针 `isMock=false` |
| 真机接管模式广播链路通 | 探针收到 `lat=37.387647 lon=117.985121 spd=3.33 brg=46.3` |
| 接管模式不污染系统定位 | 探针同时读到真实位置 `acc=550.0` |
| NPatch 在本机不可用 | `Fatal signal 4 (SIGILL) in NPatch-LogFlush` |
| LSPatch v0.6 可用 | 管理器正常、模块被识别为 Legacy API |

### 未完成（下一步）

1. 装 Shizuku + adb 拉起服务
2. LSPatch 切 Shizuku 模式
3. 管理器里给 LocProbe 启用 LocBridge 模块
4. **验证 hook 生效**（判据见 §3.3）
5. 若生效 → 观察 `hits` 计数与微信的 `dumpsys location` registration，判断微信走的是
   Java 层还是 native 直连（判据见 §4.1）
6. 按 §5 选一条落地（甲/乙/丙），取决于用户对主号数据风险的接受度

### 一句话总结

**卡住不是技术死路，是"工具链少一环（Shizuku）+ 架构上还有两道关没验证"。**
先补齐 Shizuku 把模块加载跑通，拿到 `hits` 计数这个关键观测值，
才知道微信是走 Java 层（可改）还是 native 直连（要换 hook 点或换容器）。
在此之前，"微信过不去"这个结论还不能算定论。
