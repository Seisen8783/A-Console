# LocBridge：让微信小程序读到"干净"的轨迹坐标

## 目标

让微信（包括微信小程序）里读到的位置，跟其他应用读到的一样，是一条按配速展开的连续轨迹，
并且**不带系统打上的模拟定位标记**。

## 为什么不能只靠 NoReal 现有的系统模拟

NoReal 现在的做法是注册测试定位源（`addTestProvider` + `setTestProviderLocation`），
这是系统提供的正规调试通道，代价是：

- Android 框架会给这条 provider 产出的**每一个**坐标强制打上 `isMock = true`（源码见
  `LocationProviderManager`，dumpsys 里的 `[mock]` 就是它）。
- 腾讯位置服务（微信、小程序都走它）会检查这个标记，命中就静默丢弃——
  实测表现是：系统层坐标在动、微信位置共享绿点纹丝不动，也不报错。

`cmd location` 只有测试定位源一条注入通道，`LocationShellCommand.java`（android13/14/15）
里没有任何关闭标记的参数；AOSP 里唯一不带标记的官方通道是 ADAS GNSS 注入，
但它被 `FEATURE_AUTOMOTIVE` 门禁锁着，手机上根本不显示这些命令。

所以**纯写入端这条路已经走到头**。要骗过微信，只能换注入路径。

## 原理：把"改写入端"换成"改读取端"

不去动系统的定位服务，而是直接在目标进程里，把应用读到的定位换掉：

```
微信 / 小程序
   │  LocationManager.getLastKnownLocation / getCurrentLocation / requestLocationUpdates
   ▼
LocationManager（被 LocBridge hook）
   │  替换成 new Location(...) 构造的对象
   ▼
应用拿到坐标
```

关键点在于 `new Location(provider)` 造出来的对象，`isMock` 默认就是 `false`。
我们不是"把标记去掉"，而是**给出一个本来就没有标记的坐标**，
所以下游无论做多少交叉验证（WiFi、基站、卫星、轨迹合理性），拦不住它。

## 架构

```
┌─────────────────────────────────────────────┐
│ NoReal（手机本地）                           │
│  轨迹 + 配速 + 圈数 → 每秒一帧坐标            │
│  接管模式：UDP 广播到 127.0.0.1:38765        │
└───────────────┬─────────────────────────────┘
                │ 回环 UDP，只在本机内
                ▼
┌─────────────────────────────────────────────┐
│ LocBridge（Xposed 模块）                     │
│  注入微信的全部进程：主进程 + :appbrand       │
│  · 订阅 127.0.0.1:38765 拿坐标              │
│  · hook LocationManager 三条读取路径         │
│  · hook Location.isMock() → false（兜底）    │
│  · new Location(...) 交给应用                │
└─────────────────────────────────────────────┘
```

两条接入方式可以单独用，也可以叠加：

| 方式 | NoReal 侧 | LocBridge 侧 | 能骗过微信吗 |
| --- | --- | --- | --- |
| 接管模式 | 只广播，不写系统定位源 | 构造坐标 | 能（推荐） |
| 普通模式 + 兜底 hook | 写系统定位源 | 只抹 isMock 标记 | 大概率能 |
| 普通模式 | 写系统定位源 | 不装模块 | 不能 |

## 数据协议

NoReal 每秒广播一帧 JSON（回环地址，不出手机）：

```json
{"lat":37.123456,"lon":118.123456,"spd":2.78,"brg":52.7,
 "acc":3.0,"ts":1763620000000,"ert":88123456789,"lap":1}
```

| 字段 | 含义 |
| --- | --- |
| `lat` / `lon` | WGS84 坐标（微信内部会转 GCJ-02，注入 WGS84 即正确） |
| `spd` | 速度，m/s，由配速推出 |
| `brg` | 方位角，度 |
| `acc` | 水平精度，米 |
| `ts` | 墙上时钟，毫秒 |
| `ert` | 单调时钟，纳秒（填 `elapsedRealtimeNanos`） |
| `lap` | 当前圈数 |

客户端握手：连上后先发 `SUB`，NoReal 记住来源地址，之后每秒回推一帧；
超过 2 秒没收到包就重发 `SUB` 做保活。

## 使用步骤

1. 装 **LocBridge**（`locbridge-debug.apk`），在 LSPosed（或 LSPatch）里启用它，
   作用域勾选**微信**和**系统框架**。
2. 装 **NoReal** 新版，打开「系统模拟」页，打开「接管模式 · 坐标交给 LocBridge」开关。
3. 选轨迹、设定配速与圈数，点「开始系统模拟」。
4. 看主界面提示：出现「已连接 N 个订阅者」说明模块接上了。
5. 打开 LocBridge 的界面看状态：坐标、命中次数、订阅错误都在那里。
6. 进微信小程序，位置就应该跟着轨迹走了。

改完 LocBridge 的配置（目标包名、端口）要**重启微信**才会重新加载模块。

## 怎么确认真的生效了

三个独立证据，任意一个成立就说明链路是通的：

1. NoReal 主界面：接管模式下显示「已连接 N 个订阅者」（N ≥ 1）。
2. LocBridge 界面：状态区显示坐标与「命中 N 次」。命中数是模块把假坐标交给应用的次数，
   微信只要读过一次定位就会 +1。
3. 系统层对照：`adb shell dumpsys location | grep "last location=Location\[gps"`，
   **时间戳照常推进但坐标还是真实位置**——说明位置没写进系统，是模块在读取端替换的。

小程序侧最直接的验证：在小程序里调 `wx.getLocation`，看打印出来的经纬度是不是跟着轨迹变。

## 风险与边界

- **LSPatch 会改微信 APK 的签名**。微信有自校验，被 patch 后可能闪退或触发风控。
  建议先用小号试，确认没问题再动主号。LSPosed（root 方案）不改 APK，更稳。
- **只 hook Java 层**。如果小程序的位置请求走的是微信 native 的私有路径而不是
  `LocationManager`，就不会命中。`isMock` 兜底 hook 覆盖了"拿到坐标再判断标记"的路径，
  但覆盖不了"完全绕开 LocationManager"的路径。
- **卫星状态没有伪造**。`GnssStatus` 里的卫星数、信噪比仍是真实值（模拟器里甚至是空的），
  做多源交叉验证的应用可能起疑。这一层要等后续版本。
- **坐标系**：注入的是 WGS84。高德、百度系应用需要自己转 GCJ-02/BD-09，
  同一坐标在不同应用里会差几百米。
- **微信账号风控**：反复修改位置共享可能触发异常标签。测试完先停一段时间。

## 后续可做

- 伪造 `GnssStatus`（卫星数、仰角、方位角、信噪比），补上卫星这一维。
- 伪造 WiFi 扫描结果与基站信息，让多源交叉验证自洽。
- 位置抖动模型：OU 随机游走、速度来自运动模型而非差分、精度在合理区间浮动、
  换点时模拟"失去锁定→重新收敛"，避免出现"完美直线 + 恒定速度"这种一眼假的轨迹。
- 把 `isMock` 兜底 hook 做成开关，两种模式按需切换。
- 支持更多目标应用（配置里改包名即可，模块是通用的）。
